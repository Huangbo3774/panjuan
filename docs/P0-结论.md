# P0 结论 · GO / NO-GO 记录

> 本文只写**实测过**的东西。每条都标注：测试环境、方法、原始读数。未实测的一律放在 §4「待验证」。

测试环境：Windows 11 / Chrome（内置浏览器）/ 本地静态服务 `http://127.0.0.1:8765` / Node v24.20.0
测试脚本：`tests/p0-harness.html`（可在浏览器直接打开复现，点「开始全部测试」）

---

## 1. 已得结论

### 结论 A：`pdf.js` 文本层抽取 —— **GO**
真实读数（`samples/paper-textlayer.pdf`，由 pdfkit 生成，A4 单页）：
- 页数识别 1，文本块 29 个，抽取字符 908 个
- 与原文的编辑距离相似度 **100.0%**
- 耗时 **24 ms**（热缓存；首次含跨域模块加载为 366 ms）
- 跨域 `import` jsdelivr 上的 `pdf.min.mjs` **可用**（模块加载不受 Worker 同源限制）
- 同一套判据在扫描版 PDF 上读出「文本层字符 0」⇒ **扫描件/文本层的自动分流判定成立**

**工程含义（写进 P1 的分流策略）**：只要 PDF 自带文本层，就**完全绕开 OCR**，直接拿 100% 准确的文字 + 坐标。这是整条链路最大的免费午餐，优先级必须排在 OCR 之前。

### 结论 B：跨域 Worker 的坑 —— **踩到并已定位**
现象：显式设置 `workerPath` 为 CDN 绝对 URL 且 `workerBlobURL: false` 时，
`new Worker(...)` 抛
`SecurityError: Failed to construct 'Worker': Script at 'https://cdn.jsdelivr.net/...' cannot be accessed from origin 'http://127.0.0.1:8765'`。

排查过程中的**误判**（记录以免重犯）：一开始以为是 CDN 没发 CORS 头。实测 `curl -D` 显示
jsdelivr / unpkg / esm.sh **都带 `Access-Control-Allow-Origin: *`**，头不是问题。

根因：Chrome 对 classic Worker 强制**同源**，与 CORS 无关。tesseract.js 的解法是 `workerBlobURL: true`（默认值）——先 fetch 脚本再包成同域 blob URL。我之前把它关掉了才炸。

修法：**不要覆盖 `workerPath`，不要设 `workerBlobURL:false`**，用库默认。

## 2. OCR 中文识别实测（同一把尺、同一份 ground truth）

样本：`samples/scan-cn.png`（Node 栅格化的真·中文试卷，1240×1654，墨迹 3.38%）与
`samples/scan-cn-blurry.jpg`（同一内容降采样到 620×827 + 盒模糊 + 噪点 + JPEG q0.55，模拟手机拍糊）。
两者 ground truth 见 `samples/scan-cn.ground.json`。

指标口径：`norm(s) = NFKC 归一 + 去所有空白 + 去掉下划线占位`；`sim = 1 − Levenshtein / max(len)`。
实现在 `tests/p0-harness.html` 与 `tools/ocr_rapid.py` 两处，**定义已对齐**（改一处必须同步另一处）。

| 样本 | tesseract.js（浏览器） | RapidOCR（本地 ONNX） |
|---|---|---|
| 正卷 PNG | **91.3%**（置信度 85，2485 ms） | **97.6%**（置信度 0.978，3005 ms） |
| 糊卷 JPG | **19.2%**（置信度 36，2171 ms） | **63.2%**（置信度 0.783，2126 ms） |

典型错例（tesseract.js，正卷）：`C. 镜子` → `《. 镜子`；`B` 丢失分隔写成 `B点燃`；中文被逐字拆开。
糊卷上 tesseract.js 直接把中文读成 `有 ~. BAE (SN8. RI5E)` —— **不是"准确率下降"，是整条语义崩掉**。

### G0 判定：NO-GO for 「纯浏览器 OCR」，GO for 「双档架构」

- 浏览器端 OCR（tesseract.js）在**干净印刷卷**上 91.3%，勉强可用；在**手机拍的糊卷**上 19.2%，**不可用**。
- 用户痛点③明确包含"图片打印出来看不清"，即糊卷是主场景之一 ⇒ **默认档不能只靠浏览器 OCR**。
- 决定：
  1. **首选永远是绕开 OCR**——文本层 PDF 实测 100% 相似度、24 ms（结论 A），零成本零错误；
  2. **升级档 = 本地 RapidOCR**（Apache-2.0，可商用，Python 3.11 实测可用），糊卷 63.2% 且置信度可用；
  3. **兜底档 = 浏览器 tesseract.js**，只服务"不想装任何东西"的用户，UI 上必须明示其精度限制；
  4. **P2 清洗与增强由此从"加分项"升级为"必需项"**——63.2% vs 19.2% 的差距说明预处理空间的量级；
  5. 结果**必须可编辑**：91.3%/97.6% 都意味着一份 300 字的卷子有 8–30 个错字，人工纠正是常态而非异常。

### 本环境的一个坑（记录以免重犯）
本机默认 `python` 是 **3.6.8**，装不了 RapidOCR（`protobuf requires Python >=3.7`）。
可用的是 `py -3.11`。⇒ 文档与脚本里所有本地 OCR 命令一律写 `py -3.11`，不能写 `python`。

## 3. 坏掉的尺子（自查发现，读数作废）

**读数作废 1**：本文档 §2 之前版本记录过「干净合成卷 86.7%」。该读数用的是**旧 norm**（只 `replace(/\s+/g,'')`，未做 NFKC、未去下划线），与后来 RapidOCR 用的新 norm 不是同一把尺 ⇒ **86.7% 与 91.3% 不可混用**，前者已从记录中废除。同一份样本在新尺下重测为 94.4%（合成卷）。

**读数作废 2**：`[扫描版PDF@200DPI] 相似度 0.0%（置信度 0，96 ms）`。96 ms 与空输出说明**这是尺坏了，不是内容不可读**：
- 渲染用 `getViewport({scale: 200/72})`，但 pdf.js 的默认 viewport 已是 72 DPI，`scale` 是**倍率**不是目标 DPI ⇒ 实际只渲出 829 px 宽而非 200 DPI 的 1654 px；
- 同一份 PDF 的页数被读出 **2 页**而我生成的是 1 页，说明样本生成或读取还有一处不一致，未定位。
⇒ 该场景**尚未测**，需修正尺子后重测；在此之前不得引用 0.0% 作为任何结论。

## 5. 架构决定（依据结论 A/B/G0）

1. **不做「双击 index.html 即可用」**。理由：`file://` 下 ES Module 与 Worker 均受同源限制，且 `fetch` 本地文件不可行；强行内联成单文件会让 OCR 的 blob worker 路径变得更脆弱。
   **改为**：仓库提供 `npm start`（一条命令起本地服务，自动开浏览器）。这是别人 clone 下来最常见的方式，成本一条命令，可接受。
2. 第三方库走 CDN 但**必须可一键 vendor 到本地**（`tools/vendor.js`），保证离线与断网可用。
3. 导入分流优先级固定为：**PDF 文本层 > docx 结构 > 本地 RapidOCR > 浏览器 tesseract.js**。

## 7. 外部生态调研结论（GitHub API 实测 star/更新时间/license）

**定位验证：这个闭环在开源里是空的。** 最接近的三个都不做「导入→作答→批改→带姓名得分 PDF」全链路：
- `JudgePeach/math-question-bank` 313★ / AGPL-3.0 —— PDF·Word 拆卷组卷 + A4 排版 + LaTeX，**但没有学生作答、没有批改**；且 AGPL，**不能拷代码，只能读思路**。
- `Pandlagon/IELTS-Studio` 124★ —— PDF/Word/图片→网页作答+AI 批改，但雅思专用、SpringBoot+MySQL 服务端形态。
- `QwenStorm/xl-frontend` 38★ / MIT —— K12 拍照批改 + 组卷，但是全栈 SaaS。
其余同类全部 <20★、多数无 license。**结论：值得做，且差异化点真实存在。**

### 由此产生的四条架构决定

1. **OCR 双档**（已由 §2 实测确证，不再依赖社区口碑）。因此：
   - 兜底档 = 浏览器内 tesseract.js（零安装，人人能跑）——糊卷实测仅 19.2%
   - 主力档 = 本地 `tools/ocr_rapid.py` 走 **RapidOCR**（8.2k★/Apache-2.0，ONNX）——糊卷实测 63.2%、正卷 97.6%
   - 后续可评估 **PaddleOCR**（91.3k★/Apache-2.0）能否再上一档
   - 两条路共用同一份样本与同一个 `norm()`，对比才成立
2. **导出与布局改用 `paged.js`**（1.53k★/MIT，HTML→A4 分页打印级 PDF），而不是只靠 jsPDF 手绘。理由：用户要的「文本库里随意布局」本质是 CSS 排版问题，paged.js 是现成正确答案，自研会掉进工作量黑洞。
3. **题目 JSON 对齐 IMS QTI 语义**（不自创 DSL），便于以后接题库或导出到别的系统。
4. **License 红线**：本项目 MIT。禁止引入/拷贝 AGPL 或 license 不明的代码——点名避开 `DocLayout-YOLO`(AGPL)、`MinerU`(NOASSERTION)、`Upscayl`(AGPL)、`math-question-bank` 系列(AGPL)、`M6Doc`(无 license)。可放心复用：PaddleOCR、RapidOCR、RapidLayout、docling、surya、MathLive、paged.js、OpenCV.js。

### 一个反直觉但重要的发现
**「去手写痕迹、还原空白卷」没有任何开源实现**，全是有道/百度/腾讯/合合的商业 API（合合还为此申请了专利）。所以 V1 不做「擦掉孩子手写字重新打印」——这条路要么花钱要么违法，且和「在屏幕上作答」的主路径无关。

### 关键设计决策（采纳调研建议）
**把作答尽量收在网页里完成，拍照 OCR 只作兜底。** 手写识别是开源黑洞，孩子在本机键盘作答则完全绕开它——这是本项目可行性的重要支柱，也是它和「拍照搜题」类产品正交的原因。
